# Architecture

Ruin's BlockBenchMCP has two local processes:

1. An MCP server started by the client over stdio.
2. A Blockbench plugin running inside Blockbench Desktop.

The server validates MCP input with the schemas in `src/shared`, stores staged files and checkpoints in the configured output directory, and sends authenticated requests to the plugin over `ws://127.0.0.1:<port>/bridge`. The plugin owns all calls into the Blockbench API. A random token generated by `npm run setup` authenticates both sides.

## Request path

Read-only requests can query the active project, editor state, capabilities, snapshots, and diagnostics. A model edit normally follows this path:

```text
MCP client
  -> bb_snapshot
  -> bb_plan_edit or bb_task(mode=plan)
  -> bb_apply_plan or bb_task(mode=apply)
  -> bb_diagnose / bb_capture / bb_export
```

Plans carry a project revision and explicit preconditions. The plugin rejects stale plans, protected parts, incompatible formats, busy editor state, and invalid selections before mutation. A request ID makes retries idempotent; `bb_job` reports the state of accepted work.

## Operation layers

- **High level:** `bb_task` turns an intent such as `build_model`, `layout_uv`, `paint_texture`, `animate`, `mesh_rig`, `geometry_edit`, or `project_io` into a validated plan.
- **Typed:** domain commands in `src/shared/commands.ts` provide explicit schemas and native Undo behavior for common model, UV, texture, animation, mesh, and editor operations.
- **Native:** `bb_native_operation` and related commands expose discovered Blockbench registrations (actions, controls, dialogs, settings, key bindings, panels, previews, modes, node types, codecs, and loaders) when their conditions can be evaluated.
- **Extensions:** provider plugins register their own Zod schema and execution function through the extension API.

The workflow kernel in `src/shared/workflow-core.ts` normalizes high level tasks into the same operation representation used by typed plans. This keeps validation, references, preconditions, and verification consistent across entry points.

## Files and lifecycle

`npm run setup` writes `.runtime/connection.json`, `.runtime/mcp-config.json`, and `.runtime/codex-config.toml`. These files contain local paths and a secret token and are ignored by Git. Model exports, imported files, and checkpoints are staged under the configured `artifacts` directory. The plugin can be reloaded safely; in-flight requests are cancelled and the client can inspect their final state with `bb_job`.

## Compatibility

The plugin targets Blockbench Desktop 5.1.6. The visible API is `globalThis.RuinBlockBenchMCP`; the previous `globalThis.PerfectBlockbenchMCP` name is retained as an alias so existing provider plugins can migrate without a flag day. Internal registration keys used by Blockbench project data are preserved where changing them would invalidate existing models or extensions.
